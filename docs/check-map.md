# `check()` 的结构图

> `src/by1check.py` 的 `check()`，**703–1535 行，833 行，96 条顶层语句**。
> 这份是读它的地图：18 个分段在哪、各自写下什么、三套词汇表怎么重叠、
> 以及**哪里是硬的**。
>
> 数字是 2026-02 量的一次；改动之后行号会漂 —— 分段标题（`# ---- 标题 ----`）
> 是稳定的锚点。

---

## 一、一句话

`check(path)` 吃一份 `.by1`，吐出 `(rep, info)`：

```python
rep    # 诊断（E / W / I 三档），by1check 自己印的报告
info   # 真接口 —— by1c / by1codegen / by1exec / by1ir 都只用它
```

`info` 有 24 个键：`stacks` · `expansion` · `states` · `mechs` · `d_model` ·
`vocab` · `total_layers` · `decl_params` · `tens` · `layers` · `overrides` ·
`layer_out` · `emit` · `state` · `config` · `layer_seq` · `ctx` · `hparams` ·
`position` · `named` · `layer_types` · `rope_by_type` · `mech_attrs` ·
`global_rows`

**那一份 `return`（1505–1535）就是这段代码的全部输出。** 想改什么，
先看它在不在里面。

## 三、三套词汇表怎么重叠

```
行 734 ────────────────────────────────────────── 1018   甲  语义（.by1 说了什么）
行 1019 ──────────────────────────────── 1254           乙  契约（形状）
行 1255 ────────────────────── 1411                     丙  导出（config 字段）
行 1412 ────────────── 1482                             乙  契约（状态尺寸）
行 1483 ──────────────────────── 1535                   丙  导出（数占位符 + 汇报）
```

**它大体上是按词汇表排好的** —— 三段各占一块，只有"状态尺寸"插在导出中间。
这一点比想象中好：**没有交织，是排队。**

真正的问题不是顺序，是**它们共享一个 60 个名字的命名空间**：

- 甲组写下 `layer_seq` / `mechs` / `head_dim_of`
- 乙组读它们、写下 `contracts` / `class_rows` / `states`
- 丙组读乙组的、写下 `cfg_out` / `emit_rules`

**这条链是清楚的**（甲 → 乙 → 丙）。不清楚的是那些**不在这条链上**的名字。

## 四、硬的地方（读的时候会绊到）

### ① 循环残留 —— 局部名跨段泄漏

```python
752:  for k, v in sb.assigns.items():
755:      named[k] = ex
...
862:  for k, v in pb.assigns.items():      # 同一个 k，另一段
```

`k` / `v` / `m` / `ln` / `nm` / `blk` / `h` / `hd` 这些名字在**十几个循环**里
被反复用作循环变量。后果：

- 从任何一段单独看，**读不出**它依赖谁 —— `k` 到底是这个循环的还是上个的？
- 有些地方**确实在读上一个循环的残留**（`for k, v in pb.assigns.items()`
  跑完之后，后面用 `m` —— 那是循环体里 `re.search` 的结果）

**这不是 bug**（能跑、26 份都对），**但它是"搬不动"的直接原因**：
你不知道一段需要哪些输入，因为输入取决于哪个循环最后跑过。

### ② `for k, v in ...` 里的 `k` 可能一次都没绑

```python
752:  for k, v in sb.assigns.items():
```

`sb` 是空的时候，循环一次都不跑，**`k` 根本没绑**。所以任何"把这段的参数
写成 `k=k`"的尝试都会 `UnboundLocalError` —— 这不是理论问题，
是这两天 21 次失败里的第 4、6、7 次。

### ③ 推导式里的名字不是外层的

```python
810:  _items = [x.strip() for x in split_top(_vals[1:-1]) if x.strip()]
935:  segs   = [x.strip() for x in s.split("->") if x.strip()]
```

`x` 是**推导式自己的**。看起来像"810 段漏给 935 段的值"，
但两处毫无关系。**这个假象骗过我一次**：我据此量出"16 个跨段泄漏"，
写进 `ir.md`，下一轮去修才发现是空的。

### ④ 87 行的 `stacks` 和 166 行的「张量契约实例化」

这两段占了主体的 **30%**。`stacks` 要处理命名子序列的多趟展开、
逐层覆盖、`attach` 挂载；契约那段要按等价类求值。

**它们是"值得单独读"的两段**，也是"最不想碰"的两段。

## 五、已经被切开的两处

| 切出 | 去哪 | 切之前 | 切之后 |
|---|---|---|---|
| 13 个 `gen_*` / `name_*` | `src/lang/by1export.py` | 1243 行 | 1064 行 |
| 6 个解析函数（`_coerce` `/` `parse_rope` `/` `resolve_field` …） | 同文件 | 1064 行 | 833 行 |

**两处都是"闭包搬运"**：那些是嵌在 `check()` 里的 `def`，自由变量由语言
算好，量一下就知道要传什么。切完 26 份 `.by1` 的输出**逐字节不变**。

**主体切不动的原因也正是这个**：主体不是闭包，是一段 833 行的顺序过程，
它的"自由变量"要靠数据流分析才算得出来。
