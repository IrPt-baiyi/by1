## 二、一个关键发现：`GATED_DELTA_NET` **一个原语覆盖两种模式**

它的衰减门 `g` 的形状决定语义（ops.cpp 的 `const bool kda = (neg0 == S_v)`）：

    g 的 ne[0] == 1      -> GDN 模式（逐头标量衰减）   <- by1 的 Linear
    g 的 ne[0] == S_v    -> KDA 模式（**逐维**衰减）   <- by1 的 KDA

也就是说 `Linear` 与 `KDA` 两个族**共用同一条映射路线**（都要折算：
`g = -exp(A_log)·softplus(a + dt_bias)`、`beta = sigmoid(b)`、
q/k 的 L2 归一在 op 外面做）。`qwen3-next`/`clef-tiny` 的 `Linear` 与
`kda-*` 三格，是同一件工程的四个面。

## 三、本轮已经落地的一格（样例：q_gate）

`clef-tiny` 的 Attention 阻塞里有一条 `q_gate` —— **已实现**（探针
`attn-qgate-shaped.by1`，ggml vs NumPy **7.464e-08**）。踩的坑值得留档：

> `q_gate` 的 q 投影宽一倍，但**是逐头的 `[q_hd | gate_hd]` 块**
> （参照实现 `qq.reshape(b, n, q, head_dim*2)` 再按 `:head_dim` 切）——
> 第一版按"两大半"切，`max|Δ| = 1.9e-02`，形状与名字全对、只有数值错。
> **布局类 bug 只有数值判据抓得住**（qkv_fused 的 bias 偏移那次同款）。

## 三·五、路线 ① 的调试台账（`Linear`，**未收口**）

发射器写好了（`by1ggml` 的 `elif k == "Linear"`），但数值差 **~2.7e-3** ——
按"数值没对上的实现不许冒充支持"，`check_support` **拒绝 `Linear`**。
探针 `linear-gdn-shaped.by1`（隔离用：clef 混着 q_gate，二分不了）。

已测的事实（下轮从这接）：

| 实验 | 结果 | 说明 |
|---|---|---|
| 序列长度 16 / 64 / 256 | 2.46e-3 / 2.46e-3 / 2.94e-3 | **不随长度变** —— 不是递推累积，是结构/逐元素错 |
| conv 核 1 / 2 / 4 | 1.28e-3 / 3.43e-3 / 2.7e-3 | **随核变** —— conv 的 tap 布局有嫌疑；但核 1 也错 -> 还有第二个来源 |
| rep=1（k_heads=v_heads） | 9.98e-4 | 头广播（interleave）洗清 |
| 去掉 q 的 `dk^-0.5` 预乘 | 误差变大 | 原语内部有 `scale = 1/sqrt(S_v)`；**但 RMS 归一是尺度不变的**，理论两者等价 —— 这条不一致本身也是线索 |
| `ggml_softplus` | 精确 `log1p(exp(x))`（>20 截断） | 洗清 |
| `ggml_l2_norm` | `1/max(sqrt(sum), eps)` ≠ 参照的 `1/sqrt(sum+eps)` | 差异 ~1e-8 量级，洗清 |
| 形状契约（in_proj_qkvz/ba/conv/A_log/dt_bias/norm.w/out_proj） | 逐个对上 | `norm.w` 是 `(dv,)` **逐维共享跨头**，不是 `(vd,)` |

剩余嫌疑（按优先级）：
1. **conv 的 tap 顺序/布局**（`ggml_ssm_conv` 的核序 vs 参照 `P["conv"][:, i]`；
   核 1 的残差说明还有别的）；
2. `beta`/`g` 的逐头索引（`(1, nv, n)` 的 nb1 步长）；
3. 状态转置约定（内核注释 `s_out[j*S_v+i] = S[i][j]`）与参照 `(dk, dv)` 的对齐。

### 2026-10-17 凌晨的两刀（把范围砍小了）

**① 复算脚本（build/dbg-linear.py，不入库）证明管线语义是对的**：
同一组权重、同一输入，参照公式 vs 我的 C 语义逐步对差 = **2.2e-16**
（qkvz/mix/beta/g/out/y 全部一致）—— 所以 bug **不在语义，在发射的 C**。

**② `l2_eps = 1e6` 时全对（3.5e-08）**：eps 巨大 -> L2 退化成统一缩放
（被后面的 RMS 归一吸收）-> **误差消失**；`l2_eps = 0` 仍错（2.7e-3）。
=> **根因锁定在 L2 链的逐头数值**（不是 eps 加法本身、不是递推、不是 conv）。

L2 链现状（发射的 C）：
`x / sqrt(sum_rows(x*x) + eps)`，`sum_rows` 沿 dim0（= dk）✓ 查过实现；
`ggml_add1` 要**单元素张量**（`ggml_new_f32` 装 eps）✓；`ggml_rsqrt` 不存在
（用 `ggml_div` + `ggml_sqrt`）✓；`cont_2d` 是**真重排**（cont_4d）✓。
—— 逐行都对得上但数值不对，下轮要么逐元素对拍 L2 的中间量，
要么换个构造（如把 L2 拆成"平方和"与"除法"两个节点分别验证）。

**③ 微测（build/dbg-l2.c）证明 `ggml` 的 L2 链本身是对的**：
`div(x, sqrt(add1(sum_rows(x*x), eps)))` 在已知张量上逐值正确
（sum_rows = 5/25/61/113/181/265 ✓ 结果 = x/√sum ✓）。
=> **链的构造没错；分歧在模型上下文里的用法**（形状/步长/喂进 GDN 的方式）。
注意：`l2_eps = 1e6` 通过、`0/1e-6` 失败，说明**只要 L2 的逐头归一参与**就错
—— 所以下一轮该对拍的是**模型里那三个张量**（q3/k3 归一前后 + GDN 的输入），
而不是链本身。具体做法：把 `linear-gdn-shaped` 的权重导出，
用 numpy 复算到 L2 这一步，与生成 C 的中间量对拍（在 C 里加临时打印）。

**④ C 里的自证打印（打桩 dbg_before/dbg_after）**：在生成的 model.c 里挂钩子，
算完对比 `after` 与 `before/sqrt(sum(before²)+eps)` —— **逐值一致**
（两个头都查了 ✓）；且头 0/头 1 的值相同 = interleave 的 repeat 语义正确 ✓。
=> **L2 步与 interleave 双双洗清**；`l2_eps = 1e6` 通过的机制是
"均匀分母把逐头差异掩盖"（不是 L2 本身对错）。

**剩下要对拍的只有：`q3/k3` 的值本身 vs numpy**（投影 → 卷积 → 切分这段）。
做法（下一轮）：从 `cgen-ggml-linear-gdn-shaped/w.bin` 读权重、按 ids 做
embedding 得到层输入，numpy 复算到 q3/k3，与 C 打印的 `before` 对拍。
—— 注意 `_o1_pj3`（reshape 后的逐头块）与 `_o1_cv`（卷积输出）也要打，
一次就能定位到具体哪一步。

### 2026-10-17 深夜：对拍方法立起来了，**但第一轮对拍作废**（教训）

建立了一套**双侧对拍**（下轮直接用）：
- C 侧：给生成的 `model.c` 打桩（`dbg_x` 嵌入 / `dbg_r` rms / `dbg_pj3` 投影 /
  `dbg_cv` 卷积 / `dbg_q3` 归一前），算完打印；
- numpy 侧：`build/dbg-q3.py` —— **同一套权重配方**（`default_rng(0)` +
  `shapes_of(ir)` 顺序，已逐张量对过 `w.bin` 的偏移 ✓），复算到 q3。

**但第一轮的对拍结论全部作废** —— 原因是一个可推广的调试陷阱：

> 生成的 C 里张量是在**层循环**里声明的（`_o0_r`/`v_op0_out`/`_o1_pj3` …）。
> 桩记的是指针 —— **循环跑完后它们指着最后一层**。于是"C 的 h"是层 1 的值，
> 而 numpy 算的是层 0 —— 苹果比橘子，看上去"分歧在 norm"全是假象。
> **在循环里挂钩子，必须带"只挂第 N 层"的守卫**（已加 `dbg_layer` 计数）。

有效的部分：**嵌入输出两侧完全一致**（x 的前 6 个值逐位相同）✓ ——
权重配方与 w.bin 布局都验证过 ✓。所以下一轮从"带守卫的层 0 对拍"直接开始，
预计一刀定位。

### 2026-10-17 早（第八刀）：嫌疑 ① 洗清，锁在 **mul_mat 的视图**

- 把 `ggml_cont_2d(y3, vd, n)` 换成 `ggml_reshape_2d(y3, vd, n)` ——
  **数值一模一样**（2.683e-03）⇒ `cont_2d` 的重排**不是**问题（连续张量下两者等价）；
- 变体对照（同一 `yn` 与 `out_proj`）：
  - (a) `yn @ W.T`（= 参照公式）＝ -5.9e-05 -2.6e-05 -7.0e-06 …
  - (b) `yn @ W.ravel().reshape(32, 64)` ＝ 3.0e-05 2.0e-05 5.6e-05 …
  - C 的 `out` ＝ 0.000030 0.000002 0.000002 -0.000008 -0.000023 0.000059
  ⇒ **三个都不精确一致**（(b) 的第 0 个值撞上，其余不是）；
- 权重布局已验（`params[out_proj] == w.bin[OFF_L0_OP1_OUT_PROJ:]` 逐位）✓。

**结论**：分歧不在重排、不在权重数据本身，而在 **`mul_mat` 所见的
张量视图（ne0/ne1 的解释或步长）** —— 也可能是复算脚本的变体本身算错
（`(b)` 的 reshape 语义就写错过一次）。

**下一轮一刀**：在 C 里把 `mul_mat` 的**两个输入**各取前 8 个值打出来

### 2026-10-17 早（第十刀）：**所有"一致"都只验了 t=0** —— 分歧随 token 出现

从 `v_op1_out` 的 `src[1]` 取到 matmul **真正吃的** Y（上一轮的陷阱修掉），
与 numpy 的 `yn[:, 0, 0]` 对：

```
C   Y col0: -0.00001758  0.00000068 -0.00004069  0.00001805 -0.00001603 …
numpy     : -0.00001758 -0.00005312 -0.00045237 -0.00016812  0.00000863 …
                                     ↑ 从第 1 个（t=1）起就不一样
```

**关键**：之前所有"逐位一致"的对照（x / h / pj3 / cv / q3 / y4 / y3）
都是取**前 6 个值** —— 而扁平序是 `[t][h][d]`，前 6 个**全是 t=0**。
所以那些"洗清"其实只洗清了 **t=0**；**分歧出现在 t ≥ 1**。

⇒ 嫌疑重排：
1. **因果卷积的滑窗/左补零**（t=0 只用到补零，t≥1 才用到真数据）；
2. **GDN 递推的逐 token 步**（t=0 只是初态一步，t≥1 才有累积）；
3. 之前的 `y4`/`y3`/`out` 对照要**按 token 切片**重做。

**下一轮一刀**：把对照改成**逐 token**（打印 t=0..7 各自的前 3 个值），
看分歧是"t≥1 全错"还是"t 越大差越多"（递推累积 vs 卷积滑窗的分辨法）。

### 2026-10-17 早（第十一刀）：卷积与 g 全 token 一致 —— **钉死在递推**

逐 token 对照（t=0..3 各取前 3 个值）：

| 量 | t=0 | t=1..3 |
|---|---|---|
| `cv`（卷积+silu） | ✅ | ✅ **全部一致**（嫌疑 ① 正式洗清） |
| `g`（衰减门） | ✅ | ✅ **一致** |
| `y3`（递推+RMS+norm.w+z 之后） | ✅ | ❌ **从 t=1 起不同** |

**cv 与 g 都是逐 token 一致的**，而唯一的 **token 耦合**步骤就是
`ggml_gated_delta_net` 的递推 —— 所以分歧就在：
递推的**其余输入**（`beta`/`k3`/`v3` 的逐 token 值）或**递推本身的用法**
（状态初值 / `scale` / `beta` 的逐头索引）。

**下一轮一刀**：逐 token 打 `beta`、`k3`、`v3`，若全对，则问题在
递推内核的用法（此时只剩三个可能：`s0` 的布局、`K` 参数、`scale = 1/sqrt(S_v)`
与 by1 的 `dk^-0.5` 在 `dk != dv` 时的分歧——本探针 dk==dv，需换探针或看代码）。

### 2026-10-17 早（第十二刀）：递推全对，却在 `y3` 上冒出**矛盾**

逐 token 对照（t=0..3）：

| 量 | t=0 | t≥1 |
|---|---|---|
| `cv` 卷积 / `g` 衰减门 / `z` 门控 | ✅ | ✅ **全部一致** |
| `y4`（GDN 递推输出） | ✅ | ✅ **全部一致**（递推本身洗清） |
| `y3`（= RMS(y4)·norm.w·silu(z)） | ✅ | ❌ **不同** |

**矛盾**：`y4` ✓、`z` ✓、`norm.w`（常量）✓ 都对，`y3` 却不对 ——
按公式 `y3 = y4 / √(mean(y4²)+ε) · norm.w · silu(z)` 必须相等。
⇒ **三个对照里有一个是假的**，或者 RMS 的实现与公式不符。

下一步的三个怀疑（写死）：
1. `_o1_y3` 的打印切片（`tk*32 + i` 对 (8,4,8) 是否真是 [t][h][d]）；
2. `ggml_rms_norm` 的实际归一轴/公式（用**打印出的 y4 值**手算 RMS，
   与 y3 的值对 —— 这是最直接的一刀）；
3. numpy 侧 `yn` 的计算路径（同样用手算验证）。

### 2026-10-17 早（第十三刀）：手算 RMS —— 又一个**读数假象**？

⇒ **`dbg_rms` 读到的不是 `rms_norm(y4)` 的结果**（读数假象之三），

### 2026-10-17 早（第十四刀）：**两个微测定案** —— rms 语义对、复算对，错在 `y3` 的构造

⇒ **结论：`ggml_rms_norm` 是对的、numpy 复算是对的、公式是对的，

结合前几刀：
- 内核微测（dk=dv=2, nv=2, T=3）**逐值一致** ✓；
- 视图步长（nb1=8 floats、nb2=32 floats）与内核写入公式**一致** ✓；
- 输入逐头全对 ✓；

⇒ 差异只在**模型尺寸下**（H=4、S_v=8、T=8）才显现，微测尺寸（H=2、S_v=2、T=3）
没触发。**下一轮一刀**：把微测放大到 **H=4, S_v=8, T=8**（与探针同构）——
若此时也出现"旋转一格"，就是 `ggml_gated_delta_net` 在该尺寸下的真 bug
（向上游报 + 发射侧绕开）；若微测仍对，则回到模型侧的 `y4` 视图/`res` 布局。

### 2026-10-17 早（第二十七刀）：**探针尺寸微测也全对** —— 内核彻底洗清

`build/dbg-gdn8.c`：`dk=dv=8, nv=4, T=8`（与 `linear-gdn-shaped` 同构），
值用 `sin/cos(i)` 生成，9 个采样行（3 token × 3 头）与 numpy 递推**逐位一致** ✓

⇒ `ggml_gated_delta_net` **在探针尺寸下也正确**（此前小尺寸微测 ✓ 现在同构尺寸 ✓），
内核语义与输出布局**彻底洗清**。

⇒ **"头偏移错一格"只可能来自模型侧的 `y4` 视图用法或 GDN 调用的输入布局**，
而输入 `q3/k3/v3` 已逐头对过 ✓ —— 剩下 `g` / `beta` 的布局与
`view_4d(res, …)` 的组合。

**下一轮一刀**（收窄到两处）：

## 四、剩余 11 格的实施路线（按"一处实现关几格"排）

| 路线 | 关掉的格 | 依赖 |

| ① `Linear` -> `GATED_DELTA_NET`（GDN 模式） | clef-tiny · qwen3-next 的一半 | conv/gate/z/norm 的外围照 `op_linear` 拼 |

## 五、什么会推翻这份分析

- ggml 上游**改掉**这些算子的签名（那就重新对表）；
- `op_linear`/`op_kda` 的语义与原语**差一截**（折算不出来）——
  那就按"要么实现，要么拒绝"记回矩阵，理由写**实测差异**，不再写"缺原语"。
