# By1 长期路线图

> 本文替代原来的 **1.0.0-rc0 至 rc9 行动表**。更新日期：2026-10-14。阶段按验收证据推进，不按代码行数或固定日期推进。旧版路线图与 llama.cpp 执行记录已归档到 history。
>
> **本次调整：先闭环，再扩张。** 近期主线只承诺一条从 `.by1` 到真实权重、独立参考实现、标准产物和上游运行时的可复现路径。没有完成这条路径之前，不新增模型族、量化格式或后端作为主线交付物。

## 项目要交付什么

By1 要让模型架构和权重导出规则可以被**清楚描述、机械检查、对真实产物验证**，并能借助成熟运行时执行。它的长期价值是减少架构说明、张量命名、权重共享、量化布局和模型转换之间反复手写、彼此漂移的工作。

By1 不以重新实现一个通用 LLM 运行时为目标。NumPy、PyTorch、C 和 ggml 路径承担规格验证、差分对拍和实验；实际部署优先使用经过验证的 Transformers 或 llama.cpp 上游版本。只有现成运行时确实缺少用户需要的能力时，才考虑独立补丁或新后端。所有扩展都排在一个代表模型的完整闭环之后。

### 主要交付物

- **.by1 描述**：模型机制、层排布、张量合同、共享关系、位置编码、视觉/MTP 等组件，以及导出和量化规则。
- **验证与编译工具**：从描述生成 IR、配置、权重名和 manifest；对发布方真实 checkpoint 做字段、名字、形状、dtype 和数值检查。
- **参考执行路径**：用独立实现对拍计算语义，明确支持边界；不能正确计算的机制必须明确拒绝。
- **运行时适配**：优先把标准产物交给上游 llama.cpp 等运行时，记录所需版本、命令、硬件和结果。
- **可复现证据**：每项“支持”都有真实权重、独立对照、可重跑命令和公开结果；基准数字与模型质量结论分开陈述。
- **最小可用闭环**：至少一个代表模型能够在干净环境中完成描述检查、真实权重验证、独立前向对拍、标准产物加载和短序列生成。

## 时间范围与优先级

| 时间范围 | 优先级 | 交付结果 |
|---|---|---|
| **近期：闭环主线** | P0 | 选定一个代表模型，完成干净环境安装、`.by1` 检查、真实权重与独立参考对拍、标准产物和原版 llama.cpp 加载/生成；同时清理当前验证矩阵中的失败项 |
| **中期：证据与可用性** | P1 | 将闭环扩展到第二个架构或量化模型；完成高阶门禁、独立判据、打包和跨平台复现；确认至少一个外部环境能按文档跑通 |
| **长期：扩展与发布** | P2 | 在 P0/P1 通过后推进 FP8、MXFP4、视觉/MTP、新模型族、schema 兼容和 1.0 发布门 |

阶段 A 的描述合同和拒绝规则持续维护，不要求为它另排一个大型重写。阶段 B 的上游基线和闭环主线优先；阶段 C、D、E 只能在闭环验收后进入主线。时间范围是依赖顺序，不是发布日期承诺。

## 推进阶段

### 阶段 0：完成一个可复现的最小闭环

**目标：** 证明 By1 在一个代表模型上从声明到实际运行都成立，并让第三方可以沿着同一份说明复现。

**范围：** 只选一个已有真实 checkpoint、参考实现和上游运行时支持的文本模型。优先选择体量可在普通开发机验证的模型；暂不把视觉、MTP、FP8 或 MXFP4 作为第一条闭环的必要条件。

**工作内容：**

1. 固定模型、checkpoint revision、Python/依赖版本、平台和上游 llama.cpp commit。
2. 在干净环境运行 `.by1` 检查、config/tensor 合同检查和真实权重加载。
3. 用与被测实现不同的参考路径，对固定输入比较 logits、生成 token 和权重共享关系。
4. 生成标准产物，在未修改的上游运行时中完成加载、短序列生成和最小状态复用检查。
5. 将所有命令、原始输出、阈值、跳过项和失败项写入一份可重跑报告。

**验收：** 新环境能从头跑通；每一步都有独立输入和输出；失败会以非零状态退出；跳过不会被写成通过；报告能区分配置转换正确、计算语义正确和上游部署成功这三个结论。

阶段 0 未通过前，新增模型和后端只允许作为实验分支，不进入稳定支持矩阵，也不改变 P0 的验收范围。

### 阶段 A：冻结可验证的描述合同

**目标：** 让 .by1 的描述、IR、manifest 和执行语义相互一致，发现不支持或不确定的情况时给出明确错误。

**工作内容：**

1. 整理架构字段、量化字段、权重共享和多模态组件的唯一事实来源，减少在多个检查器与后端里重复维护同一规则。
2. 为每个支持的机制记录公式、输入输出形状、dtype、状态更新方式和适用条件。
3. 为关键检查规则保留正例、负例和边界反例。缺字段、冲突配置、未知 dtype、权重别名断开和不支持的注意力模式都必须可测。
4. 给 schema 和 IR 的变更定义兼容策略；旧模型描述要么继续有效，要么由可重复的迁移工具升级。

**验收：** 现有模型描述通过快速和完整门禁；每个受影响机制有独立参考或明确的数值容差；错误输入不能静默退回到相似但不等价的实现。将新增机制纳入支持表时，同时记录真实模型或可信独立测试。

### 阶段 B：建立原版 llama.cpp 基线

**目标：** 先知道未修改的上游能做什么，并让与 By1 描述对应的标准产物在原版接口上经过真实推理验证。

**工作内容：**

1. 在仓库记录一个明确的 llama.cpp tag/commit、构建选项、CUDA 版本、GPU 型号和操作系统。源码和构建产物保持可重建，不把本机二进制当作证明。
2. 从上游已支持的架构开始，选择有真实权重且与 By1 描述对应的代表模型：至少覆盖一个普通文本模型、一个量化模型；先用发布方或社区提供的标准 GGUF 建立运行基线，再逐步验证 By1 生成的产物。视觉和 MTP 则使用确实包含这些路径的模型单独验收。
3. 用原版 llama.cpp 加载标准 GGUF，检查 tokenizer、权重张量、共享关系、前向 logits、生成 token 和多轮状态。
4. 对可比较的模型记录同一机器上的上游基准：prompt 长度、生成长度、batch、上下文、量化类型、峰值显存、prefill 和 decode 速度。将相同权重/格式下的上游数字作为运行时基线；不同精度的比较另列，不能把它说成等价对拍。
5. 收集社区派生版的补丁时，先查明其上游基线、模型专用假设、支持的设备、测试证据和许可证。社区分支是可读的实现参考，不自动成为 By1 依赖。

**验收：** 干净上游构建能复现报告；标准产物通过加载和生成；输出与对应发布方或 Transformers 参考实现的数值差在已声明阈值内；PowerShell 与 Linux 复现命令、关键结果均提供中英双语说明。

### 阶段 C：完成量化权重的直接执行（Q2）

**目标：** 量化 checkpoint 在目标运行时中保持其原生存储并参与计算，而不是双方先展开成 BF16 再比较。

**顺序：**

1. **FP8 block**：从真实 checkpoint 做原生加载、存储审计、GPU 前向、生成和显存测量；与发布方参考结果对拍。
2. **MXFP4**：覆盖 scale、打包、融合专家、未量化 bias 和非整块边界；真实权重前向与生成对拍。
3. **共享和附属分支**：逐项检查 tied embeddings、视觉塔、MTP draft head 及主干权重别名；只有模型确有该分支时才计入该模型的验收。
4. **运行质量**：比较量化模型与同一 checkpoint 的官方/高精度参考 logits、生成质量代理指标、峰值显存、加载时间及 tokens/s。说明准确度变化与速度变化的来源。

**验收：** 所有用于宣称支持的权重量化张量在运行时保留其原生 dtype/布局；没有静默反量化或 fallback；真实 GPU 测试、参考对照和重跑说明都进入报告。对某格式仅完成规格检查，不得表述为量化推理已支持。

### 阶段 D：生成量化产物（Q3）

**目标：** 从高精度权重生成可被原版工具加载的量化产物，同时保持布局、共享关系和配置语义。

**工作内容：**

1. 使用已有且维护中的格式实现作为优先选择；By1 负责描述量化合同、参数映射与验证，不为重复造轮子而实现自有 CUDA 量化器。
2. 第一批只生成 Q2 已通过的格式和架构。至少覆盖一个完整产物，含配置、tokenizer、分片索引、量化权重、未量化 tensor、视觉/MTP 附件（如存在）。
3. 重新载入生成产物，检查权重名、dtype、块数、尺度、别名、分片和总字节数；用原版 llama.cpp 跑生成。
4. 将源模型、生成后的量化模型和已有发布方量化产物并排对照，公布质量、大小、加载和速度差异。

**验收：** 产物可在干净环境中重建；标准格式可被未修改的上游加载；结构检查无缺项；数值和任务差异已记录。引入 By1 私有扩展格式之前，须先证明标准格式无法表达必要语义，并提供拒绝未知扩展的安全行为。

### 阶段 E：扩展高价值模型与多模态覆盖

**目标：** 扩展真实使用场景，而不是无限增长模型清单。

**挑选规则：**

- 优先级由用户明确需求、模型实际使用/下载趋势、架构代表性和可验证性共同决定，定期更新，不单独追逐下载排行。
- 每个候选必须有可获得的真实 checkpoint、明确许可证、参考实现和可复现的导出说明。
- 先支持能复用已有机制的新模型；只有机制或组合确实不同，才扩展 IR、格式或后端。
- 文本、图像、视频、音频、MTP、长上下文和训练分别列出支持状态，不能用“模型已支持”掩盖未验证的分支。
- 新模型先确认原版 llama.cpp 是否已支持。若已支持，By1 验证描述和标准产物；若未支持，先评估是否值得向上游贡献，再决定是否本地补丁。

**验收：** 发布的支持矩阵逐模型、逐功能注明证据、硬件、运行时版本和已知限制；没有独立判据的实验架构标为实验状态，不计入稳定覆盖数。

### 阶段 F：发布 1.0 并维持兼容

**目标：** 交付一个可安装、可复现、边界说得清的工具，而非一份不断增长的模型清单。

**1.0 发布门：**

- 干净 clone 可按文档完成安装、校验、构建和代表模型验证。
- 核心 .by1 语法与 IR 有版本和迁移说明；关键产物可重建。
- 量化、权重共享、多模态和 llama.cpp 支持矩阵区分“规格检查”“加载”“运行”“生成产物”。
- 必需检查全绿；GPU 检查可以因没有 GPU 跳过，但报告必须显示跳过，不能显示成已通过。
- 关键结论、结果表和 PowerShell 命令同时提供中文与英文说明。
- 发布前请至少一个独立环境按复现说明完成一次验证。社区发帖和营销不作为发布门槛。

## llama.cpp 兼容政策

1. **默认以原版为准。** 版本、GGUF 文件和 CLI 以 ggml-org/llama.cpp 的明确 tag/commit 为基线。
2. **标准产物优先。** By1 的架构和量化合同放在 .by1 与明确的转换输出中；不为方便临时改变 GGUF 标准语义。
3. **先核对再实现。** 开始新架构、算子、量化格式或视觉路径前，检查上游和活跃社区分支；已有能力优先做适配和验证。
4. **缺口先小补丁。** 只有上游确实缺少目标能力，且用户价值和判据明确，才开发局部补丁；补丁须单独分支、钉住上游基线、默认不改变其他架构，并配上游原版与补丁版双构建检查。
5. **尽可能上游化。** 通用 bug 或架构支持整理为上游 PR；长期本地补丁必须有负责人、跟进版本和冲突测试。
6. **自行实现设门槛。** 只有补丁长期无法合并、标准运行时确实无法表达且有可量化价值时，才考虑 By1 原生运行时；需要独立性能与正确性证据。

## 执行队列 T1–T50（闭环优先版 · 2026-10-14）

> 这是一份**顺序队列**，不是五十个并行愿望。T1–T10 组成 P0 的最小闭环；T11–T20 把闭环变成可交付的工程基线；T21–T30 扩展到第二个架构并验证标准产物；T31–T40 才进入量化；T41–T50 负责多模态、兼容和 1.0 发布。
>
> 每项都有一个可独立推翻的验收证据。代码写完不算完成；报告中必须分别列出 `pass`、`skip` 和 `fail`。当前项失败时，后续项只能做不依赖它的文档或取证工作，不能用新模型掩盖失败。
>
> **主线模型：** 默认以 `Qwen3-0.6B` 作为 P0 代表模型；如果 checkpoint、上游版本或设备条件发生变化，必须在 T1 的选择记录中说明替代物和原因。`GPT-2` 可以作为快速冒烟模型，但不能替代 P0 的完整闭环。
>
> **量级：** `S` 为半天以内，`M` 为一至两天，`L` 为数天，`XL` 为需要单独设计和复核的工作。量级用于排队，不是完成指标。

## 暂缓事项

以下事项不进入当前主线，除非真实使用场景和判卷人改变了优先级：

- 维护一个与 llama.cpp 长期分叉的完整推理引擎。
- 为已有的 CUDA/GGUF 格式重写专用量化 kernel。
- 没有真实 checkpoint 或独立参考实现的架构族。
- 把代码行数、模型文件数或固定 RC 次数当作完成指标。
- 通用后端插件协议、ONNX、扩散语言模型、自动起草描述、分布式训练和所有音视频模型的一揽子支持；这些方向等到有实际需求与独立判据再排。
- 不能复现的性能宣传或用单张合成图片推断视觉能力。
- **通用下载加速工具**（多源竞速之类）：带宽是天花板，做了也不快 —— 走影子对拍（见 T7–T11）。
- **影子模式追量化格式或图像塔**：随机字节不是合法量化块，假装验过比不验更糟；这两处只认真权重。

## 计划维护方式

每次阶段变更只写三项：**做成的用户能力、能独立推翻它的判据、复现结果的路径**。阶段验收后更新状态和报告，不因写完代码自动打勾。若上游吸收了 By1 正在做的功能，立刻重排计划，将工作改为验证、适配或删除重复实现。

**下一步：** 先按阶段 0 固定代表模型和复现环境，再从执行队列 T1 起收口基础门禁；阶段验收后更新状态和报告，写完代码不自动打勾。T31 之后的量化、视觉和扩展任务，只有在阶段 0 的报告可复现、当前失败项有归因且高阶门禁没有未解释失败时，才重新排入主线。
