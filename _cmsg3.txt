契约自动生成：把「机制声明」推成「张量契约」

先量了再动手
------------
一份 .by1 里：

    决定   707 行  27%   机制声明 + 调度 + 位置
    机械  1649 行  64%   张量契约 + 导出/命名

而 qwen3-next-shaped.by1 只有 43 行（0 行契约、0 行导出），
同样结构的 clef.by1 是 125 行 —— 差的 82 行全是机械的。

by1contract.py
--------------
从机制声明推出契约。形状写**符号**（q / head_dim / hidden / experts）
而不是数字，这样它跟着属性走。

    python by1contract.py clef.by1 [--only GQA]

判卷人是**那些对着真 checkpoint 验过的 .by1**。逐条比下来：

    形状一致   140
    形状不符    35
    只生成有    92
    只手写有   104

差异只有三个原因：

1. **打包/命名不同** —— clef 存的是融合的 `in_proj_qkv [10240]`，
   生成器给的是分开的 q/k/v（Ling 那种）。**两个都对**，
   但哪一种**是这个 checkpoint 的习惯，模板推不出来**。
2. **写死数字 vs 符号** —— glm53 那边写 `(d_model, 12288)`，
   生成器写 `(d_model, hidden)`。**生成器这边更好**；
   那边写死是因为"机制属性里的符号不参与形状求值"那个已知短板。
3. **`per_expert` 标记** —— 真漏了。已补，但它只能以**提示**形式给出
   （一个专家一个张量，还是打包成一整块，是产物的习惯）。

所以能推和推不出的边界，比我一开始以为的窄
------------------------------------------
    能推    有哪些参数、各自什么形状
    推不出  这些参数在 checkpoint 里**怎么打包成张量**、叫什么名字

以及**层/全局那一段整个推不出来**：`input_layernorm` /
`pre_attention_layernorm` / `norm` / `attn_norm` —— **四个名字指同一件事**，
纯粹是各仓库的习惯。生成器给一套默认（Llama 那一套）并明确标出来。

覆盖面和 codegen 一致
---------------------
`KDA` / `SSM` 这些 codegen 没实现的种类，生成器也没有模板，
而且它会**说出来**：

    # KDA : KDA —— 这种类没有模板（codegen 也没实现它）

这不是巧合：两边是同一个知识。**没实现的东西，两边都没有。**

顺带查实的一件
--------------
1.md 的能力清单第 8 条写着「**逃生舱**——允许直接写底层算子」。
全库检索 escape / raw_op / inline_c / native_op —— **一个都没有**。
那条是假的。
