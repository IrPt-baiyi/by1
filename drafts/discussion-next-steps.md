# 下一步做什么？—— 六个候选方向，各自带判据

**TL;DR**：by1 是一个**用声明式语法描述大模型架构、并由机器验证描述是否正确**的项目。
现在三档门禁在干净 clone 上全绿，T4 上真权重的前向/反向/更新与官方实现逐位一致。
下一步往哪走，我想听你的意见 —— 每个方向我都写清了它自己的判据和依赖。

## 现在在哪（都可复核）

- 干净 clone：档 1 **15 项 0 失败 13 跳过** · 档 3 **118 项 0 失败 31 跳过** · 档 5 **191 项 0 失败 29 跳过**
- T4（Tesla T4 16 GB）：Qwen3-0.6B **真权重** 前向 / 梯度（596M 个值）/ AdamW 一步 **逐位 0.0**，生成 token 相同
- 上游 llama.cpp `v0.6.0`（`d812350`）**未改一行源码** CUDA 构建：llama-bench pp32 **1898–2424 t/s**、tg16 **174–190 t/s**
- 细节与未验清单：[docs/gpu-validation-results.md](../docs/gpu-validation-results.md)

## 六个候选方向

| # | 方向 | 代价 | 判据（做完怎么算过） | 依赖 |
|---|---|---|---|---|
| A | **真权重扩到 8B / 27B** | 中（要更大显存） | 与官方实现前向逐位 / 1e-3 族；生成 token 一致 | ≥24 GB 显存（27B bf16 ~55 GB） |
| B | **GGUF ↔ by1 产物的 logits 逐位对拍** | 中 | `llama-eval-callback` 的 logits 与 by1 的差 ≤ 1e-3 族；同权重同输入 | 已具备（T4 上有构建和 GGUF） |
| C | **让上游 llama.cpp 支持新架构**（Zamba2 / Step-5） | 高 | 原版跑不了 -> 补丁版跑通；两边都要测 | 上游没有 `ZAMBA2` / `step5` 实现 |
| D | **蒸馏 B 层：形状搜索** | 中 | 同参数量下哪种形状蒸馏后最好（多 seed） | 已在 tiny 上跑通 15 次对照 |
| E | **架构浏览器 M5：证据叠加** | 低 | 页面上每个数字都能对回 `by1all` 的判定行 | 站点已在门禁里（`by1sitedata --check`） |
| F | **量化 Q2/Q3** | 高 | 新格式必须真实 checkpoint + 独立判据 | 卡 + 权重 |

## 我的偏好

**B 先做**：它是唯一一个"不需要新硬件、不需要新权重"就能补上的硬判据 —— 现在 by1 和上游是对着一张表说话的，
还差一次"同一份 GGUF、同一 prompt、逐 logits"的当面核对。

然后 **A 的小号**（8B，4bit）：它能把"真权重逐位"从 0.6B 推到 8B 量级，代价是一张 24 GB 卡。

**C 我持保留意见**：项目此前明确把"改 llama.cpp 本体"排除在发布目标之外（见 `docs/llamacpp-plan.md`），
理由是维护面太大。如果要做，我倾向"小补丁 + 原版对照"，而不是 fork 一个长期分支。
